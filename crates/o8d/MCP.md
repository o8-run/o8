# Experimental MCP transport

`o8d` (and the compatibility `o8d-mcp` binary) serves `/api/mcp` only with
both the `experimental-mcp` Cargo feature
and the `--experimental-mcp` runtime flag. The existing application and client
endpoints do not change automatically.

Build with:

```sh
cargo build --locked --manifest-path crates/o8d/Cargo.toml --features experimental-mcp
```

Start the TypeScript server with `O8D_MCP_READS=1`. Start the binary with an
explicit loopback `--listen` address and `--upstream` set to the current API base
resolved by the application. A listener port of zero asks the OS for a free port;
the first stdout line reports the selected listener. Point an opted-in MCP client
at that listener's `/api/mcp` URL.

The original transport remains available with those flags alone. To opt into
passive native reads as well, add `--native-reads --data-dir <absolute-data-dir>`.
`CORTEX_IDE_DB_PATH`, when set, selects the same database override as the app.
No application launcher, endpoint resolver, or default selection changes.

Native reads open the existing SQLite database with `SQLITE_OPEN_READ_ONLY`,
without `CREATE`, migrations, journal-mode changes, or `immutable`. Normal WAL
locking observes committed app writes. A replaced database inode reopens the
connection. JSON registries are opened for reading only. Native failures and
unsupported projections forward the original request to TypeScript.

The opted-in HTTP server publishes its native read policy into the existing
`app_state` table. Rust binds a new publisher generation to the configured
upstream with `o8d/read-context`, using the caller's headers. Every subsequent
read checks the live operator credential file, backend, publisher process start
identity and boot identity, generation, and server profile. Requested profiles
can only narrow that profile. Unrecognized credentials retain the original
middleware refusal. Rust never creates or substitutes a bearer.
Credential transitions retain the TypeScript clients' internal bearer-cache
window; native reads resume when both existing API clients use the current token.

The existing bounded status snapshot is also published in `app_state`, keyed by
its exact backend and session filter, retaining its capture time and 64-source
bound. Native `o8_status` projects a successful snapshot younger than five
seconds. Cold, explicitly fresh, stale, malformed, or missing snapshots return
to TypeScript, which owns live observations and refresh scheduling. Native reads
never extend snapshot age or synthesize live runtime evidence. Repository
readiness uses the same process's published readiness observations.

`o8_list_repos` reads the registry and filesystem existence. `o8_list_projects`
combines JSON metadata with SQLite membership, ordering, active selection, and
virtual repository projects. `o8_lease_list` and `o8_lease_status` read holders and waiters after
proving their current platform process identities; uncertain/dead participants and
holderless queues return to the TypeScript reconciler.

`o8_spec_read` reads an existing canonical repository's `o8.md` directly and
computes the same SHA-256 content hash. A missing file returns the API's template
without creating it. Unusual path spellings and read errors retain the original
handler. Review-index parsing, validation and annotation tools still use TypeScript.

The current mission fast path supports prepared, unbound queued packets.
Dependency/hold/release reconciliation, runtime bindings, cost and timing retain
TypeScript ownership. The compact task fast path combines those packets with
SQLite lanes; detailed/brief and explicit project-filter requests retain the
existing context resolver. Unsupported collation or source shapes also fall
back. Native publisher and lease identities follow the app's metadata-lock
contract on Linux and macOS: boot-session identity plus process start identity.
macOS reads use `proc_pidinfo` and `sysctlbyname` directly, retaining the app's
C-locale legacy timestamp format. Publisher generation binding also pins the
kernel's full microsecond start time before and after the authenticated handshake.
Every read rechecks that witness; a reused PID cannot rebind the same generation.
Lease rows retain their existing metadata-lock identity format and reconciliation
rules. Unsupported platforms and uncertain probes retain TypeScript reads. The
real-entry suite
runs native assertions on both Linux and macOS; Linux execution does not prove
macOS runtime behavior.

Legacy initialization is handled in Rust after the existing TypeScript
credential gate authorizes `o8d/read-context`, with the same response fields
and a new session ID. Catalog responses and catalog-containing batches retain
the authoritative TypeScript server's exact body bytes. Other methods/tools
and batches requiring fallback retain their original caller headers and body
bytes. Mutation batches are forwarded once. HTTP hop-by-hop and framing headers are regenerated by the
HTTP client. The TypeScript process remains required.

Both listener and upstream must be loopback. Upstream redirects are not followed.
Failed forwarding returns a fixed 503 error. If the
TypeScript opt-in is absent, native requests fall back to the original endpoint.

## Parity and measurements

The paired benchmark reports per-tool p50/p95 speedup ratios and explicit
results for the fivefold target and status p50 below 10 ms. An unmet target is
recorded as false; it is not converted into a passing performance claim. The
numeric #4374 baseline is included as historical context with `comparable: false`,
because a fixture HTTP adapter is not the baseline's source Next.js server.
The real-entry measurement test also records candidate `tools/call` forwards,
including warmups, so fallback latency is visible rather than attributed to a
native read. The six-tool outage test independently proves warmed reads need
no TypeScript requests and do not modify SQLite or the JSON registries. Native
assertions run on Linux and macOS. The publication-gate regression also runs
on Linux with a macOS platform selector and real host identity; it is not
macOS runtime or latency evidence. Measure on each actual platform separately.

Run the real HTTP fixture suite with Node 22 and Rust stable:

```sh
npx vitest run tests/o8d-mcp-parity-real-path.test.ts tests/mcp-jsonrpc-parity.test.ts
```

The fixture uses the production middleware, MCP host, read APIs and persisted
lanes/projects/leases. Only external runtime/auth observations and screenshots
are fixture replacements. `tests/fixtures/mcp-parity/requests.json` records tool
calls, argument variants, profiles, batches, notifications and malformed input.
The fixture binds its generated repo path to `$FIXTURE_REPO`. Additional native
credential and profile refusals are recorded in `native-reads.json`, consumed by
`tests/o8d-mcp-parity-real-path.test.ts` in the test named
`replays additional native credential and profile refusals`. The suite
also covers committed WAL updates without writes, missing databases, publisher
binding, token rotation, reconciliation fallback, and snapshot boundaries.

For two already-running opted-in listeners, set `O8_MCP_PARITY_TOKEN` in the
process environment and run:

```sh
node --import=tsx scripts/mcp-parity.ts --reference="$REFERENCE_API_BASE" --candidate="$CANDIDATE_API_BASE" --recording=tests/fixtures/mcp-parity/portable.json
```

The comparator checks status, protocol headers, JSON-RPC fields, array positions,
and JSON nested inside text content. Catalog responses, including batches,
also require byte-identical bodies. Missing/extra fields fail. Valid timestamps
named `capturedAt`, `createdAt`, `updatedAt`, `decidedAt`, `generatedAt`, `checkedAt`, `observedAt`
or `timestamp` may differ; other freshness differences require exact JSON pointer
declarations in the recording. Only the documented freshness field names are
accepted. Types and field presence must still match. Mismatch reports include
field paths, without state values or credentials.

For reproducible latency numbers, build the optimized binary, set
`O8D_MCP_TEST_BINARY` to its absolute path and `O8_MCP_BENCH_REPORT` to a workspace
JSON output path, then run the real fixture suite's test named
`measures both servers with the existing speed MCP client`. This status-only gate
requires native p50 and p95 at most TypeScript / 5 and zero forwarded candidate
calls. It interleaves both servers, alternates their order, uses 10 warmups and
100 measured samples per path (110 calls each), and calls the same `rpc` client
and `distribution` helper as `scripts/speed/mcp.mjs`. The benchmark CLI's default
still measures all tools; `--tools=o8_status` selects the paired status gate. Reports
contain sample counts, p50 (`median`) and p95 milliseconds. The native candidate
is explicitly enabled and warmed, including publisher
generation binding. Fallback requests remain included. These numbers include
HTTP client and transport costs, and the shared status snapshot behavior. They
describe the fixture
HTTP adapter, not a production Next.js process, and establish no speedup claim.

## Scale and event-loop load

From the repository root on Linux with Node 22 and Rust stable, regenerate the
raw samples with this exact command sequence:

```sh
cargo build --locked --manifest-path crates/o8d/Cargo.toml --release --features experimental-mcp
benchmark_dir="$(mktemp -d)"
O8D_MCP_TEST_BINARY="$PWD/crates/o8d/target/release/o8d-mcp" \
O8_MCP_SCALE_BENCH_REPORT_DIR="$benchmark_dir" \
npx vitest run tests/o8d-mcp-parity-real-path.test.ts -t 'realistic state'
printf 'Raw samples: %s\n' "$benchmark_dir"
```

The generated `large-idle.json` and `large-cpu-busy.json` stay in that temporary
directory. Do not commit the raw samples.

The fixture contains 300 missions, 2,000 packets and lanes, 50 initialized Git
repositories, 10 projects and 200 leases. There are 276 archived missions and
144 active lanes; the current mission has six bound packets. Lease owners use
one live fixture process identity. External runtime/account observations remain
fixture replacements. Bulk seeding requires the canonical database path to be
the owned fixture database before any mutation.

The test checks parity on this state before running `scripts/mcp-benchmark.mjs`
twice, with 10 warmups and 100 samples per operation and server. The idle run
has no injected CPU work. The busy run schedules 100 ms synchronous CPU blocks
every 125 ms on the TypeScript fixture's event loop. Timers can be delayed by
the application's own synchronous work, so reports include actual busy time,
cycle count, observed duty and event-loop delay. The benchmark client and Rust
listener run in separate processes. Run other builds and tests separately from
sampling.

`large-idle.json` and `large-cpu-busy.json` include fixture cardinalities and
TypeScript fallback counts, including warmups, for every read tool. The counts
subtract the 110 reference requests from the observed TypeScript MCP calls;
they describe this serial, interleaved paired client. Rust endpoint timings
include its TypeScript fallbacks. Bound mission and task projections in this
fixture retain those fallbacks, and status can fall back when its shared
snapshot needs refresh. These measurements use the fixture HTTP adapter and
synthetic CPU work; they do not measure a production Next.js deployment.

## Recorded scale summary

Machine class: Linux development environment. CPU model, memory capacity and
virtualization details were not recorded in the original receipt. Both cohorts
used Node 22.23.4 and a Rust release build. No builds or other test suites ran
during sampling.

Each tool has 100 measured samples per server per cohort, after 10 warmups.
Values below are p50 / p95 in milliseconds. Rust endpoint values include
TypeScript fallback.

Fallback counts cover all 110 candidate requests per tool, including warmups.
The CPU-loaded cohort completed 1,160 synchronous blocks, with 116,029 ms of
injected CPU work over 358,543 ms (32.4% observed duty). It requested 100 ms
blocks every 125 ms; application work delayed the timer.

Bound mission and task requests fell back on every call. Status refreshes still
produced roughly two-second Rust endpoint p95. These fixture measurements do
not establish an across-the-board 5x speedup. A later `terminalReason: null`
parity alignment applies to prepared, unbound missions, which these bound
mission cohorts do not exercise.
